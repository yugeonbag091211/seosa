# SEOSA 전수 감사 — 미해결 · 보류

마지막 갱신: 2026-11-24 00:05 KST

## 보류 — 운영 판단이 필요하다 (코드로 고칠 일이 아니다)

### R-01 중단된 스케줄 3개 (F-02)

`SEOSA HOT`, `Volatile Price Rechecks`, `SEOSA Product Identity Shadow` 가
2026-11-14 에 GitHub Actions 에서 `disabled_manually` 로 멈췄다. 같은 날 Neon
전송량 비상이 있었으므로 **의도된 비용 조치로 보인다**.

- 켜지 않은 이유: Production 동작과 Neon 사용량을 바꾸는 일이고, 비용 한도는
  감사자가 정할 수 있는 값이 아니다.
- 켜지 않으면 남는 것:
  - 홈 핫딜의 «SEOSA 검증» 배지가 영구히 뜨지 않는다(60건 중 0건).
  - 낮·저녁 가격 재확인이 돌지 않는다.
  - `SEOSA HOT` 안에 있는 커뮤니티 사진 백필도 같이 멈춰서 F-08 의 죽은 사진이 쌓인다.
- 필요한 결정: Neon 여유가 돌아왔는지, 돌아왔다면 셋 중 무엇부터 켤지.
- 안 켤 거라면 화면 문구를 현실에 맞추는 선택지가 있다(배지 안내문 삭제) —
  그것도 제품 결정이라 손대지 않았다.

### R-02 `no-store` 로 꺼진 CDN 캐시 (F-03)

`/api/search` 와 `/p/:pid` 가 `IDENTITY_CANONICAL_CONSUMER_ROLLOUT_PERCENT > 0`
때문에 상시 `no-store` 다. 사이트맵이 광고하는 상품 URL 21,980개가 전부 여기 해당한다.

- 롤아웃 대상은 사용자가 아니라 `groupKey` 해시로 정해지므로 같은 주소는 같은
  결과를 준다 — 즉 캐시해도 변종이 섞이지 않는다.
- 바꾸지 않은 이유: 코드 주석이 «중단을 즉시 반영하려고 매 요청에서 상태를 읽는다»
  라고 근거를 밝히고 있다. 캐시를 켜면 percent 를 내렸을 때 최대 s-maxage 만큼
  늦게 반영된다. 그 trade-off 는 운영자의 것이다.
- 필요한 결정: 전환이 FINALIZE 됐다면 «롤아웃 중» 분기를 끄는 환경변수를 둘지,
  아니면 짧은(60초) 캐시를 허용할지.

### R-03 `/api/search` 의 예산 조건 해석 (F-04)

«10만원 이하 이어폰» 같은 검색어의 가격 조건이 무시된다. 넣으려면 회수율이
바뀌므로 봉인 holdout 으로 전후를 재야 한다. 이번 감사 범위에서 제외했다.

### R-07 계절이 지난 하드코딩 큐레이션 목록 (F-07)

`_shop.TODAY_PICKS` 가 한여름 목록이다. 고치려면 «무엇으로 바꿀까» 를 정해야 한다.

- `api/init.js` 는 이미 `_picks.demandPicks` 로 막아 뒀다(인기 검색어 우선).
- 안 막힌 곳: `api/rec.js` 의 두 자리(폴백·빈 프로필), `api/cron.js` 수집 키워드.
- 가장 작은 선택지: `api/rec.js` 도 `demandPicks` 를 쓰게 한다. 다만 `/api/rec` 에
  `search_stats` 조회가 한 번 늘어난다 — 그 비용을 감수할지가 결정 사항이다.

### R-09 영문 검색어가 공급자 단계에서 걸리지 않는다 (F-11)

`airpods` 는 결과 6건이 전부 액세서리이고 실제 에어팟이 0건이다. 쿠팡 카탈로그가
한글 «에어팟» 으로 적혀 있어서 영문 질의가 공급자에서 매칭되지 않는다.
`_search.js` 의 동의어 그룹(`['airpods','에어팟']`)은 **받아온 목록을 재정렬할 때**만
쓰이고, 공급자에게 보내는 검색어에는 적용되지 않는다.

- 바꾸지 않은 이유: 질의 확장은 공급자 호출 수와 회수율을 함께 바꾼다.
  쿠팡·ADPICK 분당 한도가 이미 병목이라(메모리 기준) 호출을 늘리는 변경은 측정 없이 못 넣는다.
- 필요한 결정: 영문 질의일 때 한글 동의어로 한 번 더 부를지, 아니면 결과 0건일 때만 부를지.

## 미해결 — 더 큰 검증이 필요하다

### R-04 판매 대상(sold object) 판정이 기존 랭커에 없다 (F-05)

«맥북에어 M4» 1·2위가 액정보호필름(본품은 3위), «게이밍 노트북» 에 책상,
«노트북» 에 가방, «아이패드» 에 원데이 클래스·투어, «커피머신» 에 책이
본품과 같은 1.00 을 받는다.

판정 코드는 이미 있다 — `api/_search2-object-relation.js` (Search 2.1).
다만 `?engine=mini21` 로만 켜지는 베타이고, 기존 랭커에 끌어오면 «무엇이
떨어지는가» 가 바뀐다. 전후를 같은 세트로 재지 않고 넣으면 안 된다.

필요한 것: 아직 쓰지 않은 holdout 질의 세트. (메모리 기준으로 기존 봉인
holdout 두 벌은 이미 소진됐다.)

특히 어려운 쪽: `아트박스/힐링쉴드 맥북에어13 M4 M5 ARAG 고화질 저반사 1매 외부3종`
처럼 **제목에 «필름/케이스» 같은 부속 낱말이 아예 없는 부속**. 지금 규칙은 걸 자리가 없다.

### R-05 검색 지연의 원인 (F-06)

22회 중 5회가 10초를 넘었고 최악이 41.8초였다. 공급자 타임아웃(쿠팡 8s + 대기 1.5s,
ADPICK 15s, 둘은 병렬)으로는 설명이 안 되는 구간이 25초 이상 남는다.
Vercel 함수 로그 없이는 어느 단계인지 특정할 수 없다.

필요한 것: 운영 로그, 또는 각 단계에 타이밍 계측을 넣은 Preview 배포.

## 환경 제약으로 못 한 것

### R-06 운영 DB 직접 조회

로컬 `.env.local` 에 `NEON_DATABASE_URL` 이 없다(`SUPABASE_URL` /
`SUPABASE_SECRET_KEY` 는 있으나 운영 DB 는 Neon 으로 옮겨졌다).
그래서 아래는 **공개 API 응답으로 보이는 범위까지만** 확인했다.

- `price_history` 중복·유실 여부
- 수집 성공률의 실제 분모
- `hotdeals` 표가 비어 있는지 vs 조건에 걸러지는지의 구분

필요한 것: 읽기 전용 Neon 접속 문자열, 또는 운영자가 직접 돌린 조회 결과.

### R-08 레이트리미트 우회 가능성 (미검증)

`api/_ratelimit.js` `clientKey()` 는 `x-forwarded-for` 의 **첫 번째** 값을 쓴다.
Vercel 이 클라이언트가 보낸 `x-forwarded-for` 를 덮어쓰는지 앞에 붙이는지에 따라
헤더만으로 `/api/search` 의 30회/분 관문을 우회할 수 있다.

확인하려면 운영에 위조 헤더를 넣은 요청을 반복해야 한다 — 쿠팡 쿼터를 태우고
운영 원장에 쓰기 때문에 하지 않았다. Preview 배포에서 확인하는 편이 맞다.
