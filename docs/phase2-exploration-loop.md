# Phase 2 — Exploration Loop 구현 메모

Phase 1(2026-08-29 UX 개편)에서는 **만들지 않은** 기능이다. 여기서는 다음에
구현할 때 "무엇을 새로 만들고 무엇을 재사용하면 되는가"만 정리한다.

목표 루프:

```
상품 A → 비슷한 상품 → 더 저렴한 상품 → 상품 B → A vs B 비교 → AI 판단 → 관련 탐색
```

---

## 1. 이미 있는 것 (재사용 대상)

### 1-1. 유사 상품 판별 엔진 — `Compare` (public/index.html)

Phase 2 에서 가장 값비싼 부분이 **이미 만들어져 있다.** 새 추천 엔진을 쓰지 말 것.

| 함수 | 하는 일 | Phase 2 에서의 쓰임 |
|---|---|---|
| `Compare.keywordOf(title)` | 상품명 → 검색 키워드(앞 3단어, 특수문자 제거) | "비슷한 상품" 후보를 가져올 검색어 |
| `Compare.tokensOf(title)` | 상품명 → 토큰(2자 이상) | 유사도 계산 입력 |
| `Compare.GENERIC` | 색상·연결방식·포장 등 변별력 없는 불용어 표 | 오탐 방지 (이미 실사고 기반으로 채워져 있음) |
| `Compare.isGeneric(t)` | 불용어 + 치수/용량 토큰 판정 | 위와 동일 |
| `Compare.keyTokensOf(title)` | 브랜드·모델명만 남긴 핵심 토큰 | **유사도 점수의 핵심** |

**핵심 아이디어**: 지금 이 엔진은 "같은 상품인가"(높은 토큰 일치)를 판정하는 데만
쓰인다. **임계값을 낮추면 그대로 "비슷한 상품"이 된다.** 즉 필요한 것은 새 알고리즘이
아니라 *임계 구간 하나*다.

```
일치도 높음  → 같은 상품 (현재 몰별 비교가 쓰는 구간)
일치도 중간  → 비슷한 상품  ← Phase 2 가 쓸 구간
일치도 낮음  → 무관
```

### 1-2. 데이터 공급 — 신규 API 불필요

| 필요한 것 | 기존 경로 |
|---|---|
| 비슷한 상품 후보 | `Api.call('searchAndSave', [kw])` — `Compare.open()` 이 이미 이렇게 가져온다 |
| 더 저렴한 상품 | 위 결과셋을 `lprice` 로 필터/정렬. 추가 호출 0회 |
| 가격 이력 | `HistCache` + `/api/history-batch` — `Grid.fillSparklines()` 가 이미 채운다 |
| 가격 통계(avg30/low/trend) | `PriceStat.from(hist)` |
| 매수 판정 문구 | 서버 `api/_pricestat.js` 의 `assess()` / `VERDICT_LABEL` |
| AI 질문 | `Chat.open()` + `Chat.prefill(text)` (Phase 1 에서 추가) |

`Compare.cache` 가 키워드별 검색 결과를 세션 동안 재사용하므로, 같은 상품에서
"몰별 비교"와 "비슷한 상품"을 잇달아 열어도 외부 API 를 다시 때리지 않는다.

### 1-3. 표시 컴포넌트

| 컴포넌트 | 재사용 방법 |
|---|---|
| `Grid.render(el, items)` | 비슷한/더 저렴한 상품 목록을 기존 카드로 그대로 그린다 |
| `Grid.markWhy(sparkBox, hist)` | 카드 근거 한 줄 (Phase 1 에서 추가) |
| `Card.read(cardEl)` | 카드 → 상품 정보. A/B 선택 시 그대로 사용 |
| `.cmp-table` CSS (index.html ~426) | 비교표 스타일이 이미 있다 |
| `Nav.aiPrompt(ctx)` | `ctx` 분기만 추가하면 A/B 비교용 질문 문구 생성 |

## 2. 새로 만들어야 하는 것

1. **유사도 임계값 함수** — `Compare.similarityOf(titleA, titleB)`
   `keyTokensOf` 교집합 / 합집합 정도면 충분하다. 같은 상품(현행 판정)과
   비슷한 상품을 가르는 경계값은 실제 데이터로 맞춰야 한다.

2. **"비슷한 상품" 목록 UI** — 상품 상세 모달 하단. `Grid.render` 재사용.

3. **A/B 비교 선택 상태** — 상품 2개를 고르는 UI(체크 또는 "비교에 추가").
   `AppState` 에 `comparePair: []` 정도만 추가.

4. **A vs B 비교표** — 가격 / 30일 평균 대비 / 기록 최저 / 신뢰도 / 몰.
   전부 이미 있는 값이라 계산 로직은 필요 없고 표만 그리면 된다.

5. **analytics 이벤트 2개** — `related_product_click`, `comparison_open`(A/B 구분용).
   `api/_analytics.js` 의 `METRICS` 배열에 이름을 **반드시 같이 추가**할 것.
   빠뜨리면 프론트는 정상으로 보이는데 집계만 조용히 안 된다.

## 3. 용어 — 섞지 말 것

Phase 1 에서 문구를 분리해 두었다. 코드에서도 같은 구분을 유지한다.

| | **몰별 가격 비교** (현존) | **상품 비교** (Phase 2) |
|---|---|---|
| 사용자 질문 | "이 상품을 **어디서** 싸게 사나" | "**어느 상품**이 나에게 맞나" |
| 대상 | 동일 상품 × 여러 몰 | 서로 다른 상품 2개 |
| 진입 | `Compare.open()` / `data-act="card-compare"` | 신규 |
| 모달 | `#cmpOverlay` | 신규(같은 모달에 얹지 말 것 — 두 질문이 섞인다) |

## 4. 하지 말 것

- 새 추천 API 를 만들지 말 것. 위 표대로 기존 검색·이력 경로로 충분하다.
- 추천 근거에 사용자의 과거 행동을 쓰지 말 것("최근 ~를 검색해서"). Phase 1 의
  `Grid.markWhy` 와 같은 규칙 — 상품의 가격 사실만 쓴다. 개인화 근거는
  섹션 헤더에서 한 번만 밝힌다.
- `Chat.send()` 를 자동 호출하지 말 것. 로그인 벽이 갑자기 뜬다.
  Phase 1 처럼 `Chat.prefill()` 로 채우고 전송은 사용자가 하게 한다.
