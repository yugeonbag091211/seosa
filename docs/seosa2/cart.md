> 계약: [CONTRACTS.md §3 ⑤](CONTRACTS.md). 이 문서는 그 계약을 **어떻게** 구현했고, 무엇을 가정하며, 어디까지 못 하는지 적는다.

| 파일 | 역할 |

## 1. 흐름

```
본문 검증 (400 BAD_INPUT)
  → 기준 행   products: product_id (in, 60개 청크) — 없으면 상품명 검색(ilike 단서 1~2개, ≤60행)
  → 후보군    products: 기준 행의 keyword 로 최근 수집 60행 (검색어마다 1회, 병렬)
  → 동일상품  judgeSameProduct tier A  AND  _hotgroup.canMerge  (df = 후보군 제목의 modelCodeFrequency)
  → 가격 확인 loadStats(받아들인 오퍼) → lastPrice 우선, 없으면 카탈로그 lprice
  → LIVE/STALE productLifecycle 'live' 이고 관측이 MAX_DISPLAY_AGE_DAYS(10일) 안이면 LIVE
  → 최적화    LIVE 오퍼만, 상품마다 정확히 하나
  → 기준선 · 절약액 · 가정
```

조회 횟수는 상품 수와 무관하게 «상수 × 상품 수» 를 넘지 않는다 (상품명만 준 상품당 최대 2회, 서로 다른 검색어당 1회).
어떤 표에도 쓰지 않고, 외부 쇼핑 API 를 부르지 않는다.

## 2. 같은 상품 판정 — 합치지 않는 쪽으로

`_hotgroup.js` 첫 주석의 원칙(**false merge < duplicate**)을 그대로 따른다.

| 경우 | 결과 | 사용자에게 보이는 이유 |
|---|---|---|
| 기준 행 그 자체 | 받아들임 | — |
| tier A + canMerge 통과 | 받아들임 | (option.notes 에 «제목으로 모델·용량·색상·수량이 같은지까지 확인») |
| 같은 product_id · 같은 몰 · 다른 vendor_item_id | 제외 | 다른 옵션이에요 |
| 용량 / 색상 / 수량 / 모델 / 연식 / 세대 / 형태 / 묶음이 다름 | 제외 | 해당 옵션이 달라요 (예: `256gb ≠ 512gb`) |
| tier A 인데 canMerge 탈락 | 제외 | 스펙 숫자·가격 차이·모델코드 변별력 등 |
| 그 밖의 tier B/C | 제외 | 동일 상품 확신 부족 |
| 오래 확인 못 함 (STALE) | 제외 (목록에는 남김) | 최근 가격 확인이 안 돼 판매·재고 여부를 알 수 없어요 |

- 제외 목록에는 **근처 후보**(제목 자카드 ≥ 0.5)만 최대 12개 보여 준다. 같은 검색어에 섞인 케이스·충전기 같은 무관한 상품은
  개수만 `assumptions` 에 한 줄로 적는다. 이 값은 «무엇을 보여 줄지» 만 정하고 병합에는 쓰지 않는다.
- canMerge 규칙상 **서로 다른 쿠팡 상품 번호 두 개는 합쳐지지 않는다** (둘 다 옵션 번호가 있고 서로 다르므로).
  쿠팡 ↔ ADPICK 판매몰 사이의 같은 상품만 제목으로 잇는다. 놓치는 진짜 중복이 있지만 안전한 방향이다.
- 상품명만 준 경우에는 검색 결과 중 **tier A** 만 기준으로 삼는다. 짧은 상품명("갤럭시 S24")은 대개 tier A 가 아니므로
  `unresolved` 로 돌려주고, tier B/C 후보 최대 3개를 `suggestions` 로 제안한다 (화면에서 눌러 상품 번호로 바꾼다).

## 3. 비용 모델

몰(=판매처, `mallLabel`) m 의 소계 S_m 에 대해

```
배송비(S)  = 0                       (S = 0, 그 몰에서 안 산다)
           = 0                       (freeOver != null 이고 S ≥ freeOver)
           = fee                     (그 밖)
쿠폰(c, S) = 0                       (S < minSpend)
           = min(amount | ⌊S·percent/100⌋, maxDiscount, S)
총액       = Σ 단가×수량 + Σ_m [ 배송비(S_m) − max_c 쿠폰(c, S_m) ]
```

- 판매처 이름: 쿠팡 행은 `'쿠팡'`, ADPICK 행은 `mall_label`(11번가, G마켓 …). ADPICK 인데 이름이 없으면 **상품마다 따로** 센다
  (같다고 가정하면 배송비를 적게 세어 총액을 낮게 말한다).
- 배송비: 사용자 입력 → 기본 추정치 `{ fee: 3000, freeOver: 30000 }` (모든 판매처 동일, 판매처별 정책을 지어내지 않는다).
- 쿠폰: **사용자가 입력한 것만**, 몰마다 가장 유리한 **하나만**. 최소 주문 금액과 무료배송 기준은 모두 **배송비·쿠폰 적용 전 상품 소계**로 판정한다.
- 입력 판매처 이름은 공백·대소문자를 무시하고 맞춘다(`' 11번가 '` = `'11번가'`).

## 4. 최적화 — 정확 분기 한정

상품마다 LIVE 오퍼 하나를 고르는 문제다. 무료배송 기준·쿠폰 최소 금액이 몰 소계의 계단 함수라 (배낭 문제를 품고 있어)
다항 시간 정확해는 기대할 수 없다. 그래서 **정확한 분기 한정**으로 풀고, 노드 상한(200,000)에 걸리면 `optimal:false` 로 말한다.

**준비**
- 줄 안에서 (몰, 금액)이 같은 후보는 하나만 남긴다(총액이 몰 소계에만 달려 있으므로). 같은 몰의 **더 비싼** 후보는 버리지 않는다 —
  무료배송 기준을 넘기려고 같은 몰에서 조금 비싼 옵션을 고르는 것이 이득일 수 있다(테스트로 고정).
- 줄 순서: 후보 수 오름차순 → 값 차이 내림차순. 자식은 «넣으면 총액이 가장 적게 느는» 순.
- 같은 상품을 여러 줄로 담아 줄이 똑같으면 대칭을 깬다(뒤 줄은 앞 줄 선택 이상만) — 맞바꾼 배정은 총액·택배 수가 같다.

**시작 해** — 탐욕 + 국소 개선, **상품별 최저가 배정**, **단일 몰 배정**. 기준선 자체를 시작 해로 넣으므로 계획 총액은
노드 상한에 걸려도 두 기준선보다 클 수 없다 → 절약액 ≥ 0 이 구조적으로 보장되고, 코드는 그래도 확인해서 어기면 멈춘다.

**하한 (admissible)** — 계약이 적은 기본형(고른 값 + 남은 줄 최저값 − 몰별 최대 쿠폰, 배송비 0)보다 항상 크거나 같은 두 하한의 최댓값.

1. **몰별 분해.** 총액 = 고른 값 + Σ 남은 줄 최저값 + Σ_m [웃돈_m + 배송비_m − 쿠폰_m]. «웃돈» 은 그 몰로 보낸 줄이 자기 최저값보다 더 낸 돈이다.
   몰마다 괄호를 혼자 최소화하면(줄을 여러 몰이 나눠 가져도 된다고 풀면) 합은 실제 이하다. 한 몰 안에서는 기준 금액(무료배송·쿠폰 최소 주문) 사이
   구간마다 «구간을 채우는 최소 웃돈(분수 배낭 곡선, 깊이마다 미리 계산) + 그 구간의 (배송비 − 쿠폰)» 을 아래에서 막고,
   정률 쿠폰은 쿠폰마다 볼록 문제로 정확히 최소화한다 (`배송비 − max_c D_c = min_c(배송비 − D_c)`).
2. **쿠폰 합의 상한.** 모든 몰의 쿠폰 최소 금액을 한꺼번에 채울 돈은 없다. 쿠폰마다 `D ≤ min(cap, rate·S)` 인 오목 덮개로 총 지출 상한 안에서
   쿠폰 합의 상한을 분수 배낭으로 구한다.

**동점** — 총액이 같으면 택배(몰) 수가 적은 쪽.

**올바름 검증** — `test-v2-cart.js` 가 결정론 난수 550개 사례(1~5 상품 · 1~4 후보 · 1~4 몰 · 무작위 배송비/정액·정률/최소금액/최대할인)에서
독립 구현한 완전 탐색과 **같은 최저 총액·같은 택배 수**, 같은 두 기준선을 내는지 확인한다. 개발 중에는 1~8 줄 4,000개로도 대조해 불일치 0이었다.

**복잡도** — 최악은 O(Π 후보 수) 노드(상한 200,000), 노드당 O(몰 수 × (기준 금액 수 + 쿠폰 수) × log 후보 수). 실측(Node 22, 20 상품, 각 200개):

| 사례군 | 노드 중앙값 | p95 | 최대 | 최대 시간 | 상한 도달 |
|---|---|---|---|---|---|
| 현실형 (후보 1~4 · 몰 1~5 · 값 제각각) | 13 | 554 | 17,661 | 14ms | 0/200 |
| 넓은형 (후보 1~6 · 몰 1~6) | 27 | 47,207 | 200,000 | 88ms | 5/200 |
| 적대형 (값이 전부 ±20% 안, 후보 1~6) | 28 | 19,635 | 200,000 | 146ms | 3/200 |
| 적대형 (값이 전부 ±20% 안, 모든 상품 6곳 · 6몰) | 3,613 | 200,000 | 200,000 | 250ms | 19/200 |

상한에 걸린 사례를 상한 500만으로 다시 풀어 본 표본에서는 상한 안에서 찾은 해가 이미 최적이었고, 증명만 끝나지 않았다.
그래도 증명하지 못했으면 `optimal:false` 와 함께 «최저가가 아닐 수 있어요» 를 `assumptions` 에 적는다.

## 5. 기준선

- `cheapestEach` — 상품마다 단가가 가장 싼 LIVE 오퍼, 그 배정에 **실제 배송비·쿠폰**을 적용한 총액.
- `singleMall` — 모든 (계산 가능한) 상품을 LIVE 로 파는 몰 중, 그 몰 안에서만 최적화한 총액이 가장 싼 곳. 없으면 `null`.
- `savings.vsSingleMall` · `vsCheapestEach` = 기준선 − 계획 (≥ 0).

## 6. 사용자에게 드러내는 가정 (`assumptions`)

- 재고 API 가 없다 — 최근 10일 안에 가격을 확인한 판매처만 판매 중으로 본다.
- 가격은 SEOSA 가 마지막으로 확인한 값(가장 오래된 확인일 표시) — 결제 전 판매처에서 확인.
- 가격 기록이 없어 카탈로그 가격을 쓴 판매처 수.
- 배송비를 입력하지 않은 판매처와 기본 추정치(3,000원 · 30,000원 이상 무료) — «판매처마다 달라요, 입력하면 정확해져요».
- 배송비는 판매처마다 한 번, 무료배송 기준은 쿠폰 전 금액 — 오픈마켓은 판매자마다 따로 붙을 수 있다.
- 쿠폰은 입력한 것만, 몰당 하나 / 입력한 쿠폰이 없으면 쿠폰 없이 계산.
- 비교할 상품이 없어 못 쓴 쿠폰·배송비 입력, 이름 없는 ADPICK 판매처를 따로 센 사실, 비교하지 않은 무관한 후보 수, 탐색 한도 도달.

## 7. 계약을 해석한 곳

| 질문 | 결정 |
|---|---|
| `offers` 에 STALE 도 넣는가 | 아니다. `offers` = 계산에 쓴 LIVE 오퍼, STALE 은 `excluded` 에 `{offer(availability:'STALE'), reason}` 으로 |
| `freeOver` 가 없거나 0 | 없음(`null`) = 무료배송 기준 없음(항상 fee), `0` = 항상 무료 |
| 배송비 입력에 `fee` 가 없음 | 400 — `fee` 는 필수, `freeOver` 만 선택 |
| 쿠폰 `amount` 와 `percent` 둘 다 | 400 (하나만) |
| 본문 32KB 초과 | 413 이 아니라 계약의 입력 오류 규칙대로 400 `BAD_INPUT` |
| 계산할 상품이 하나도 없음 | 200, `plan.byMall: []` · 합계 0, `singleMall: null`, 전부 `unresolved` |
| 판매처별 기본 배송비 | 지어내지 않는다 — 모든 판매처에 같은 추정치 |
| 계약에 없는 추가 필드 | `Offer.priceSource` (`'price_history'`\|`'catalog'`), `byMall[].shippingEstimated`, `unresolved[] = { itemIndex, input, reason, suggestions[] }` |
| 하한 | 계약이 적은 형태보다 조인 형태(더 많이 자르고 여전히 과소평가) — 완전 탐색 대조로 확인 |
| 요청한 `vendorItemId` 가 카탈로그에 없음 | 같은 상품의 다른 옵션 가격을 빌려 오지 않는다 → `unresolved`, 다른 옵션들은 `excluded` |

## 8. 한계

- **재고·쿠폰·배송 정책을 모른다.** 판매 중 여부는 최근 관측뿐이고, 배송비는 입력이 없으면 추정이다. 로켓배송·와우·묶음배송 정책을 반영하지 않는다.
- **오픈마켓의 판매자 단위 배송비**를 모른다 — 11번가·G마켓은 판매자마다 배송비가 따로일 수 있는데 판매처(몰) 단위로 한 번 센다.
- **후보는 같은 검색어(keyword)로 수집된 최근 60행**뿐이다. 다른 검색어로 수집된 같은 상품은 찾지 못한다.
- 서로 다른 쿠팡 상품 번호는 합치지 않는다(판매자가 다른 같은 상품도 비교에서 빠진다).
- 가격은 파트너스 API 의 관측가라 실제 결제가(카드 할인·와우가)와 다를 수 있다.
- 조합이 아주 조밀하면(모든 상품이 비슷한 값으로 6곳 이상) 20만 노드 안에 증명이 끝나지 않을 수 있다 → `optimal:false`.
- 단일 몰 기준선은 몰마다 2만 노드 안에서 구한다. 한 몰에 같은 상품의 후보가 아주 많으면 그 몰의 최적이 아닐 수 있다(계획은 그래도 그 값 이하).
