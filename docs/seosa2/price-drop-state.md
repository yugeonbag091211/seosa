# 가격 하락 상태표 (PR #88) — 설계 · 측정 · 운영 절차

`/api/init`의 홈 «가격 하락» 후보(상위 200)를 요청마다 계산하던 `price_drop_top` 뷰 대신,
옵션 키별로 미리 계산해 둔 **세대별 상태표**에서 읽는다. 마이그레이션:
`supabase/2026-09-25-price-drop-state.sql` · 확인 `…VERIFY.sql`(운영 안전) · 되돌리기 `…ROLLBACK.sql` ·
테스트 DB 전용 전체 대조 `…TESTDB-PARITY.sql`.

## 왜

- 운영: `price_drop_top` 3/3 HTTP 500, 8,642–8,688ms 뒤 SQLSTATE 57014 (#84 뒤에도). PR #86 RPC도 7초 한도에 취소.
- 원인: 요청마다 `price_history` 최근 30일 전체를 옵션별로 순위 매기고 전체 기간 최저가를 집계한다. 원장이 커질수록 다시 느려진다.

## 결과가 기존 뷰와 같은 이유

옵션 키마다 «날짜가 가장 늦은 관측 2개»와 전체 최저가를 저장한다. 기존 뷰의 30일 창은 아래로만 막혀 있으므로
«전체 중 최신 2개»의 직전 관측이 창 안이면 곧 «창 안의 최신 2개»이고, 창 밖이면 기존 뷰에서도 빠진다.
그래서 창은 **조회 시점에** `prev_date >= current_date - 30`으로만 건다 — 날짜가 지나도 상태표를 다시 쓸 필요가 없다.
`__LEGACY__`/NULL 옵션 제외, 날짜 없는 관측은 최저가에만, 하락률 산식, `products` 내부 조인은 그대로다.

## A. 원자적 전체 재구성 — 세대(generation)

| 방식 | 공개 시 비용 | 부분 노출 | 되돌리기 | 채택 |
|---|---|---|---|---|
| **세대 번호 + 메타 `published_gen` 한 칸 교체** | 한 행 UPDATE | 없음 (읽기는 공개 세대만) | 직전 세대로 한 행 UPDATE | ✅ |
| staging 표 → 한 트랜잭션에서 delete+insert 복사 | 전체 복사 · 매번 팽창 | 없음 | 다시 복사 | |
| 표 `RENAME` 교체 | ACCESS EXCLUSIVE 잠금 | 없음 | 다시 교체 | 뷰가 OID로 묶여 이름을 따라가지 않음 |
| 구체화 뷰 `REFRESH CONCURRENTLY` | 매번 전체 계산(운영 8초+) | 없음 | 없음 | 배치로 못 나눔 |

흐름: `rebuild_start(owner)` → `rebuild_step(gen, owner, 3000)` × N → `publish(gen, owner)`.

- **한 번에 하나:** 소유 토큰 + 하트비트. 다른 소유자가 10분 안에 하트비트를 남겼으면 `busy`(중복 크론). 10분 넘게 조용하면
  커서에서 인수하고, 옛 소유자의 다음 배치는 `lost build ownership`으로 거부된다.
- **중간 장애:** 배치는 한 트랜잭션이라 끊기면 롤백되고 커서가 그대로다. 같은 소유자·다음 실행이 이어받는다. 공개 세대는 그대로.
- **증분·배치·공개는 같은 권고 잠금**(대기형)으로 한 번에 하나만 쓴다 — 서로 다른 스냅숏의 계산이 뒤섞이지 않는다.
  재구성 중 증분은 공개 세대와 재구성 세대에 모두 쓴다.
- **공개 게이트** (하나라도 실패하면 예외 → 공개 세대 그대로):
  1. 모든 배치 완료
  2. 따라잡기: 재구성 시작 뒤 기록된 상품(최근 창 ∪ 시작 시 max id 뒤 INSERT)을 다시 계산
  3. 행 수가 공개 중인 세대의 90% 미만이면 거부 (반쪽 재구성)
  4. 표본 검증: 어긋난 상품을 한 번 다시 계산한 뒤에도 어긋나면 거부 · `products` 조인 중복 0
- 공개 뒤 공개·직전 세대만 남긴다.

## B. 안전한 VERIFY — 기존 뷰를 부르지 않는다

`price_drop_state_verify(gen, sample, record)`는 표본 키만 `price_history`에서 **그 키의 행만**(인덱스) 읽어 독립적으로 다시 계산한다.

- 표본: 사용자에게 보이는 상위 N(하락률) · 무작위 N · 30일 경계 ±1일 · 최근 원장 기록 N(누락 탐지)
- 대조: 최신가·최신일, 직전가·직전일(= 30일 창 소속), 전체 기간 최저가, 하락률 산식, 동일 옵션 키, 누락(missing)·잉여(extra),
  `products` 조인 중복
- 마지막 증분 뒤 새 기록이 있는 키는 `pending`으로 따로 센다(잘못된 공개가 아니라 아직 안 돈 것)
- 운영 `VERIFY.sql`은 `p_record => false`로 불러 아무것도 쓰지 않고, `statement_timeout`을 올리지 않는다
- 기존 뷰와의 전체 양방향 EXCEPT ALL은 테스트 DB 전용(`TESTDB-PARITY.sql`)

## C. 증분 · 탐지 · 복구

| 변경 | 처리 |
|---|---|
| 오늘 기록, 같은 날 재수집(가격 수정) | 증분 — `recorded_date >= current_date - 2` 상품을 원장에서 통째로 다시 계산 |
| 과거 날짜 가져오기(INSERT) | 증분 — `id > id_watermark - 10000` 상품 (커밋 순서 차이는 겹침으로 흡수) |
| 같은 키·같은 날 중복 기록 | 원장 UNIQUE가 막는다 |
| 삭제 | `pg_stat_user_tables.n_tup_del` 증가 → `needs_rebuild` → 원자적 재구성 |
| 과거 행 가격 정정 · 옵션 번호 변경 | 표본 검증 불일치 → `needs_rebuild` → 원자적 재구성. 표본에 안 걸리면 **일일 재구성(KST 10:40)이 상한 ≤ 1일** |
| 갱신 실패 · 중복 크론 | 공개 세대는 그대로. 다음 실행이 이어받는다. 홈은 `todayDropConfirmed`가 오늘 원장으로 다시 확인하므로 낡은 후보는 걸러질 뿐 «틀린 하락»은 나가지 않는다 |

자동 모드(`scripts/refresh-price-drop-state.js`): 미초기화·`needs_rebuild`면 원자적 재구성 → 아니면 증분 → 표본 검증 → 불일치면 재구성 → 다시 검증.

### PGlite (WASM Postgres 17, 단일 연결) — 원장 260,311행

현재 뷰 356ms · #86 RPC 236ms · 상태표 3.6ms · 증분 305ms · 전체 재구성 0.75–1.0초.

### 한계 — 운영 성능이 아니다

로컬 데스크톱의 따뜻한 캐시다. 운영(무료 Supabase)에서 기존 뷰는 8.6초로 로컬의 약 24배였다. 같은 배율이면 상태표 조회는 수십 ms,
증분 수 초, 배치 1–3초로 **추정**할 뿐이다(함수 한도 60초). 이전 무료 테스트 Supabase 측정 14.9ms도 운영 성능이 아니다.
운영 수치는 적용 뒤 `VERIFY.sql` §5 계획과 `/api/init` 응답 시간으로 다시 잰다.

### 비용

- 저장공간 ≈ 세대 2개 23MB 수준 (무료 500MB 한도 대비 약 5%).
- DB 계산: 증분이 수집 실행마다(하루 최대 18회) + 낮 4회, 일일 재구성 1회. 외부 API 호출 0, 쓰기는 상태표·메타뿐.
- GitHub Actions: 공개 저장소라 분 과금 없음.

## 운영 적용 순서 (각 단계 별도 승인)

1. 가격 수집 시간대(KST 00–09시)를 피해 `2026-09-25-price-drop-state.sql` 적용 (2초 lock_timeout, 새 객체만).
2. `VERIFY.sql` §1 권한 확인.
3. 수동 실행 `Price Drop State (gated)` mode=`full` (또는 로컬 `node scripts/refresh-price-drop-state.js --full`) → 첫 세대 공개.
4. `VERIFY.sql` §2·§3·§5 — `ok=true`, `mismatches=0`, 계획에 `price_drop_state_rank_idx`.
5. 저장소 변수 `PRICE_DROP_STATE_ENABLED=1` → 수집 뒤 자동 갱신 시작.
6. Vercel `PRICE_DROP_SOURCE=state` → 재배포 → `/api/init` 시세판 응답·시간 확인.

## 장애 대응 · 되돌리기

| 상황 | 조치 |
|---|---|
| 새 세대가 틀렸다 | `--rollback` (또는 수동 mode=rollback) — 직전 세대로 한 행 UPDATE, 즉시 반영 |
| 재구성이 멈췄다 | 다음 실행이 10분 뒤 커서에서 인수. 버리려면 `--abort` (공개 세대 유지) |
| 공개가 거부됐다 | 워크플로 로그의 사유(행 수·검증) 확인 → 원인 해결 뒤 `--full`, 아니면 `--abort` |
| 증분·검증이 계속 실패 | `PRICE_DROP_STATE_ENABLED` 삭제(갱신 정지) → Vercel `PRICE_DROP_SOURCE` 삭제(기존 뷰로) |
| 완전히 걷어낸다 | `PRICE_DROP_SOURCE` 삭제·재배포 → `PRICE_DROP_STATE_ENABLED` 삭제 → `ROLLBACK.sql` (파생 데이터만 삭제) |
| 가져오기·정리 스크립트로 원장 과거 행을 고쳤다 | `--full` (삭제는 자동 탐지되지만 과거 행 UPDATE는 일일 재구성까지 늦을 수 있다) |

첫 판(세대 없는 상태표)을 적용한 테스트 DB는 마이그레이션이 멈추며 알린다 → `ROLLBACK.sql` 뒤 다시 적용.
