# SEOSA 기술 SEO — 구조와 정책 (2026-10-02, 레드팀 후속 반영)

검색엔진(Google · 네이버)이 SEOSA 를 «상품별 최저가 · 가격 추이를 기록하는 가격비교 서비스» 로
읽게 하는 장치를 한곳에 적는다. 코드의 주석이 근거를, 이 문서는 지도를 맡는다.
이 문서와 코드가 다르면 코드가 틀렸거나 문서가 낡은 것이다 — `scripts/test-seo.js` 가 아래 규칙을 고정한다.

## 1. URL 구조

| 주소 | 무엇 | 렌더 | 구현 |
|---|---|---|---|
| `/` | 홈 (SPA) | 정적 HTML + JS | `public/index.html` |
| `/p/{product_id}` | 상품 1개 (판매처 1곳의 기록) | 서버 렌더 | `api/_product-page.js` |
| `/category` | 카테고리·브랜드 허브 | 서버 렌더 | `api/_seo-pages.js` |
| `/category/{slug}` | 카테고리 (예: `/category/laptop`) | 서버 렌더 | `api/_seo-pages.js` |
| `/brand/{slug}` | 브랜드 (예: `/brand/lg`) | 서버 렌더 | `api/_seo-pages.js` |
| `/sitemap.xml` | 사이트맵 인덱스 | 서버 | `api/_seo-pages.js` |
| `/sitemaps/pages.xml` · `/sitemaps/products-N.xml` | 사이트맵 파일 | 서버 | `api/_seo-pages.js` |

* 상품 주소는 바꾸지 않았다. `/p/{id}` 는 이미 공유·색인되고 있고, 쿠팡 상품명은 길고 옵션이
  섞여 slug 로 얻는 것보다 주소가 바뀌는 위험이 크다.
* 새 서버리스 함수는 없다. 전부 `api/history.js` 의 `__route` 갈래다 (Vercel Hobby 12개 상한).

## 2. 색인 정책

| 페이지 | 색인 | 조건 |
|---|---|---|
| 홈 `/` | index | — |
| 상품 `/p/{id}` | index | `isIndexableProduct`: live(수집 10일 이내 · 쿠팡/ADPICK · 가격>0) · 판매처 링크 · 구매 가격(렌탈·구독·100원 미만 아님) · **현재 옵션(vendor_item_id) 관측 7일 이상** |
| 상품 (위 조건 미달) | **noindex,follow** | 페이지는 열린다 (사용자·공유용) |
| 카테고리·브랜드 | index | **본품 8개 이상 AND 그중 상품 페이지가 index 인 것 3개 이상** (둘 다) |
| 카테고리·브랜드 (미달) | **noindex,follow** | 데이터가 쌓이면 자동으로 index. 본품 0개면 404 |
| 허브 `/category` | index | 색인 묶음 3개 이상. 허브는 index 인 묶음에만 링크한다 |
| 검색 `/?q=` · 딥링크 `/?p=` · `/index.html?q=` · `/index.html?p=` | **noindex,follow** | `X-Robots-Tag` 헤더(vercel.json) — 남은 한계는 §9 |
| 내 레이더 `/radar.html` | **noindex,follow** | 개인 저장 목록 |
| `/api/*` | robots.txt 차단 | 크롤러가 쿠팡 호출 한도를 태우지 않게 |

* **상품 색인 규칙은 한 곳이다.** `api/_product-page.js` 의 `observedDays`(현재 옵션의 KST 관측일 수 —
  `_price.sameVendorRows`) 와 `isIndexableProduct` 를 상품 페이지와 폴백 사이트맵이 같이 쓰고,
  `supabase/2026-10-02-seo-sitemap.sql` 이 같은 규칙을 SQL 로 옮긴다. 한쪽을 고치면 셋 다 고친다.
* **목록 색인의 «기록 상품 3개» 는 상품 사이트맵과 같은 목록으로 센다** (`eligibleProductIds`).
  2026-10-02 운영 재현(SQL 규칙 2,012개 기준): 70개 묶음 중 index 35 · noindex 35.
  SQL 미적용(폴백) 상태에서는 폴백 목록이 일부만 담으므로 더 적다 (로컬 실측 33).
* **robots.txt 로 막는 것과 noindex 는 다르다.** robots 로 막으면 크롤러가 noindex 를 읽지 못해
  주소만 색인될 수 있다. 그래서 `/?q=` · `/p/` · `/category` 는 robots 로 막지 않는다.
* 사이트맵에는 index 인 주소만 들어간다 (Search Console «제출됐지만 noindex» 방지).

## 3. 카테고리·브랜드는 «사람이 고른 목록» 이다

`api/_seo.js` 의 `CATEGORIES` · `BRANDS`. 검색어마다 페이지를 만들지 않는다 (doorway page).

* 2026-10-02 실측: 상품 8개 이상인 짧은 검색어가 1,835개였지만 사용자 문장이 섞여 있고
  ("더 싼 데일리 향수 찾기 로 검색해드릴까요?") 같은 개념이 여러 검색어로 갈라져 있다.
* 카테고리 하나 = 개념 하나 = 검색어 여러 개 (마우스 = 마우스 · 무선 마우스 · 게이밍 마우스).
* 브랜드 = 상품명 첫 낱말이 별칭과 정확히 같을 때만. «호환» 상품 · LG생활건강 · 몰 이름 머리는 제외.
* 추가할 때: 운영 DB 에서 그 검색어의 «live 본품» 이 11개 이상인지 확인하고 한 줄 더한다.
  색인 여부는 그 뒤에도 실제 데이터(§2)가 정한다.

목록에 드는 상품 (카테고리): live · 링크 · 구매 가격 · 관련성(`relevantRows`) · 본품
(`filterMainProductCandidates`) · 카테고리 중앙값의 20% 이상(키캡·어댑터·가방을 거른다).
목록에 드는 상품 (브랜드): 첫 낱말 별칭 · 본품 · **카테고리 검색어로 모인 행이면 그 카테고리 본품일 것**.

* 카테고리 목록은 현재가 낮은 순, 브랜드 목록은 현재가 높은 순 (TV 와 리모컨을 견주지 않는다).
* **«가장 낮은 ○○ 상품은 …» 같은 단정 문장을 쓰지 않는다.** 목록 1위가 본품이 아닌 행이 남아 있다
  (2026-10-02: 바디로션 1위 «로션 병», 쌀 1위 «쌀조청»). 수치는 «목록 현재가 범위 · 중앙값» 으로만 말한다.

## 4. 구조화 데이터 (JSON-LD)

| 페이지 | 스키마 |
|---|---|
| 홈 | `WebSite` + `SearchAction`, `Organization` (기존) |
| 상품 (index · 가격 있음 · 마지막 관측 3일 이내) | `BreadcrumbList`, `WebPage`, `Product` + `Offer`(1곳) |
| 상품 (그 밖) | `BreadcrumbList`, `WebPage` — **Product 없음** |
| 카테고리·브랜드 | `BreadcrumbList`, `CollectionPage` + `ItemList`(상세 URL) — Product 없음 |

* **가격** — 화면 큰 글씨와 같은 값(마지막 관측가). `review` · `aggregateRating` · `availability` 는
  넣지 않는다 — SEOSA 에 그 데이터가 없다.
* **오래된 가격 (3일)** — 마지막 관측이 오늘(KST)로부터 3일을 넘으면 Product 를 통째로 뺀다
  (`_seo.STALE_OFFER_DAYS`). 묵은 값을 현재가 Offer 로 내지 않기 위해서이고, Offer 만 빼면 Product 가
  제품 스니펫 필수 조건을 못 채워 «잘못된 항목» 이 되므로 Product 째 뺀다. **페이지 색인 여부는
  이 규칙과 무관하다** (색인은 §2 의 10일 규칙).
* **판매자 (`seller`)** — `_seo.sellerOf`.
  쿠팡 → «쿠팡» · ADPICK + 실제 몰 이름(`mall_label`) → 그 이름 · **ADPICK + 몰 이름 없음 → seller 생략**.
  «ADPICK» 은 제휴 네트워크라 판매자로 쓰지 않는다 (운영 ADPICK 행의 99.7% 가 몰 이름이 비어 있다).
  meta description 도 판매처를 모르면 몰 이름을 쓰지 않는다. (화면 버튼 «ADPICK에서 보기» 는 SPA 와
  같은 기존 표시라 이 PR 에서 바꾸지 않았다.)
* **카테고리 breadcrumb · brand** — `_seo-pages.productContext`.
  카테고리 목록에 실제로 드는 본품일 때만 «홈 › 카테고리 › 상품», 아니면 «홈 › 상품».
  brand 는 첫 낱말 별칭 + 본품 판정(부속 낱말이면 탈락) + 카테고리 검색어 상품이면 카테고리 본품일 것.
  «LG 그램 전용 어댑터» · «닌텐도 스위치 OLED 전용 필름» · «애플 호환 케이스» 는 brand 없음.
  판정할 수 없으면(조회 실패) 둘 다 비운다 — 틀린 계층보다 짧은 계층이 낫다.
* 판매처가 2곳 이상인 경우를 위한 `AggregateOffer` 는 공용 함수에 있지만 상품 페이지는 1곳이라 쓰지 않는다.
* 직렬화는 `_seo.jsonLdScript` 하나로 한다 (`< > & U+2028 U+2029` 이스케이프 — `</script>` 주입 방지).

## 5. 사이트맵

* `/sitemap.xml` → `pages.xml` + `products-1..N.xml`. 상품 파일 하나는 `products.id` 40,000 폭의
  반열린 구간 `[(N-1)·40000, N·40000)` (URL 상한 45,000 < 프로토콜 50,000). 비어 있는 범위는 인덱스에 없다.
* **기본(primary) 경로** — DB 함수 `seo_sitemap_products` (supabase/2026-10-02-seo-sitemap.sql) 가 범위별로
  전수 판정한다. 2026-10-02 재현값 약 **2,012개** (범위별 1632 · 242 · 14 · 41 · 83 · 0).
* **폴백 경로** — 함수가 없을 때만. `indexableProducts` 가 묶인 양(이력 40페이지 · 상품 10페이지)만 읽어
  `products-1.xml` 하나로 낸다. 전수가 아니다 (2026-10-02: 약 1,140개). 대신 같은 판정 함수를 써서
  **담은 URL 은 전부 index** 다 (예전 폴백은 옵션을 구분하지 않아 2% 가 noindex 였다).
  매 요청 운영 DB 전체를 훑지 않는다.
* **`pages.xml` 은 항상 인덱스에 있다.** 상품 사이트맵 계산과 무관하다.
* **부분 실패** — 범위 하나가 실패해도 나머지는 낸다(로그 남김).
  실패한 범위는 같은 인스턴스의 직전 정상 결과로 대신한다. 직전 결과가 없으면 그 범위는 인덱스에서 빠지고
  그 파일은 503 이다.
* **급감 방어** — 한 범위 또는 전체가 직전보다 절반 미만으로 줄면(직전 ≥ 20개) 직전 결과를 유지한다.
  «0개·반토막을 200 으로 정상 처리» 하지 않기 위해서다. 직전 결과는 **24시간** 이 지나면 기준으로 쓰지 않는다
  (진짜로 줄어든 경우 옛 목록을 영원히 붙들지 않는다). 직전 결과는 서버리스 인스턴스 메모리뿐이라
  갓 뜬 인스턴스에는 비교 기준이 없다 — 새 저장소는 만들지 않았다.
* **형식이 틀린 RPC 응답**(배열이 아님)은 «0개 성공» 이 아니라 실패로 다룬다.
* **503** — 전부 실패했고 직전 결과도 없으면 `503 + Retry-After + Cache-Control: no-store`.
  크롤러는 나중에 다시 오고 이미 아는 URL 을 버리지 않는다. 카테고리·브랜드·허브 페이지의 데이터 오류도
  같은 503 이다(`api/history.js`). 직전 결과로 대신한 응답은 10분만 캐시한다(평소 12시간).
* **lastmod** — 상품: 수집일의 **KST 날짜** (SQL·폴백 둘 다). 카테고리·브랜드: 목록 상품의 마지막 수집일(KST).
  홈·허브: **생략** — 실제 변경일을 알 수 없는데 매 요청 «오늘» 을 찍지 않는다.
* `/sitemap-products.xml`(예전 주소)은 같은 인덱스를 낸다 — 이미 제출된 주소가 깨지지 않는다.

## 6. 404 · 품절 · 삭제

| 상황 | 응답 |
|---|---|
| 없는 `product_id` (지워졌거나 수집된 적 없음) | 404 + noindex · **canonical 없음** (짧게 캐시) |
| 수집이 10일 넘게 끊김 (stale) · 연동이 끊긴 몰 | 200 + noindex — 기록은 남아 있다 |
| 판매처 링크 없음 | 200 + noindex |
| 레지스트리에 없는 카테고리·브랜드 slug | 404 · **canonical 없음** |
| 레지스트리에 있지만 상품 0개 | 404 · canonical 없음 (soft 404 금지) |

* 410 은 쓰지 않는다. «영구 삭제» 와 «아직 수집 안 됨» 을 DB 로 가를 수 없다.
* 품절 상태는 모른다 (쿠팡 검색 API 에 재고 필드가 없다). 재고를 추측해 표시하지 않는다.
* 판매처 하나가 사라져도 상품 페이지는 지우지 않는다 — 링크가 없으면 noindex 로 내려간다.

## 7. 중복

* 상품 하나 = `(product_id, mall)` 한 행 = 주소 하나. 운영 DB 에 product_id 가 두 몰에 걸친 행은
  0건이다 (2026-10-02). `?m=` · `?mall=` · utm 이 붙어도 canonical 은 `/p/{id}` 하나다.
* 옵션(vendor_item_id) 이 다른 것은 다른 상품이다 — 합치지 않는다. 같은 물건이 재등록돼 다른
  product_id 를 가진 경우도 합치지 않는다 (`_hotgroup` 원칙: 잘못 합치는 것 < 중복).

## 8. 비용 (DB 조회)

| 경로 | 조회 |
|---|---|
| 상품 페이지 | 기존과 같음 + **카테고리 검색어 상품만 카테고리 목록 조회 1회** (본품 판정). 같은 인스턴스에서 같은 카테고리는 10분 재사용 |
| 카테고리 페이지 | 목록 1–4페이지 + 가격 기록(표시 60개) + 색인 판정 목록(상품 사이트맵 메모 공유) |
| 브랜드 페이지 | 목록 + 관련 카테고리 본품 집합(메모) + 가격 기록 + 색인 판정 목록 |
| 허브 · pages.xml | 카테고리 4묶음 + 브랜드 1묶음 + 색인 판정 목록, 10분 메모 |
| 사이트맵 | SQL: 존재 확인 + max(id) + 범위당 RPC 1회 · 폴백: 묶인 읽기(이력 40 · 상품 10페이지), 10분 메모 |

* 2026-10-02 로컬(→ 운영 DB) 실측: 상품 페이지 카테고리 키워드 평균 1.07s(최악 2.37s) · 카테고리 밖 0.89s(최악 1.97s),
  같은 카테고리 연속 0.88s. **SQL 미적용(폴백) 상태에서는 인스턴스의 첫 목록 요청이 7–10s** (폴백 계산 1회),
  이후 10분은 0.5–1s. Edge 캐시(1h + SWR 4h)가 대부분을 가린다. SQL 을 적용하면 폴백 계산이 RPC 로 바뀐다.

## 9. 남은 한계 (후속 PR)

* **검색 URL 의 원본 HTML 모순** — `/?q=…` · `/index.html?q=…` 응답은 `X-Robots-Tag: noindex, follow`
  헤더를 받지만, `index.html` 은 정적 파일이라 원본 HTML 에는 `meta robots=index,follow` 와
  `canonical=https://seosa.ai.kr/` 가 그대로 있다. 인라인 스크립트가 실행되면(렌더링 크롤러) canonical 을
  떼고 robots 를 noindex 로 맞추지만, JS 를 실행하지 않는 크롤러는 헤더 noindex 와 HTML 의 index·canonical 을
  동시에 받는다 (헤더의 noindex 가 더 제한적이라 우선한다). 서버 응답부터 일원화하려면 이 경로를 서버 함수로
  보내 머리를 바꿔야 하는데, Vercel 이 `/` 를 파일시스템에서 먼저 서빙하는지(빌드 출력 설정)를 preview 로
  확인할 수 없고(SSO) 625KB HTML 을 함수 번들에 넣는 위험이 있어 이 PR 에서는 하지 않았다.
